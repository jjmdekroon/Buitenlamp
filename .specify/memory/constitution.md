# Buitenlamp Constitution

Buitenlamp produces ESPHome firmware (a YAML configuration with short C++ lambdas) for an ESP32
microcontroller that controls an outdoor lamp and integrates with Home Assistant. This
constitution governs every specification, plan, task list, and device configuration in this
repository.

## Core Principles

### I. Fail-Safe Hardware Behavior (NON-NEGOTIABLE)

- Every output MUST be in a defined, safe state from the earliest point at boot. Lamp outputs
  MUST use `restore_mode: ALWAYS_OFF` (or the equivalent for the component), so they start OFF
  unless the feature spec states otherwise.
- After power loss, brownout, or reset, the device MUST return to a defined state without user
  intervention. Lamp state MUST NOT be restored from flash unless the feature spec asks for it.
- ESPHome's task watchdog MUST stay enabled. No configuration option or lambda may disable it;
  a hung loop MUST lead to a reset, not a stuck output.
- Loads above a pin's rated current (relays, LED strips, mains lamps) MUST be switched via a
  driver (transistor, MOSFET, level-shifting buffer, or relay module); the configuration MUST
  NOT assume a pin can drive them directly.
- Sensor inputs that decide switching (light level, motion, buttons) MUST be filtered with
  ESPHome filters (`delayed_on`, `delayed_off`, `settle`, or equivalent) or hysteresis, so the
  lamp never flickers or chatters at a threshold.

Rationale: the device runs unattended outdoors and may switch mains-powered loads; a wrong or
oscillating output is a safety and hardware-lifetime risk.

### II. Non-Blocking Automations

- Lambdas MUST NOT block: no `delay()`, no busy-wait, and no single lambda may run longer than
  10 ms. Waiting MUST use ESPHome's non-blocking actions (`delay`, `wait_until`, scripts).
- Any time arithmetic in lambdas MUST use `millis()` with unsigned subtraction
  (`now - last >= interval`), so it survives the ~49.7-day `millis()` rollover.
- Behavior with more than two modes MUST be an explicit state machine: named states held in
  `globals` (or a `select`), with the transitions kept together in named scripts.
- Project code MUST NOT install its own interrupt service routines; interrupts are used only
  through ESPHome components.

Rationale: a blocked loop misses sensor events, starves the watchdog and the network stack, and
makes timing behavior impossible to reason about.

### III. Bounded Resource Usage

- Project lambdas that run repeatedly (per loop, per update, per sensor value) MUST NOT allocate
  heap memory: no `new`/`malloc`, and no building or growing `std::string` in those paths.
  Allocation inside ESPHome and its framework is accepted.
- After each build, static RAM usage MUST stay at or below 75% of the target's SRAM and flash
  usage at or below 90%, as reported by the build.
- Flash writes (ESPHome preferences, `restore_value`) MUST happen only for values the feature
  spec requires to persist, and only when the value actually changes.

Rationale: an unattended device fails silently when memory fragments or flash wears out; flash
cells survive a limited number of writes.

### IV. Declarative, Traceable Configuration

- Hardware (pins, platforms, chipsets, electrical modes) MUST be declared once, in the
  component definitions. Automations, scripts and lambdas MUST refer to entities by `id`, never
  to pin numbers.
- Decision logic (when the lamp turns on or off, timers, modes, overrides) MUST live in named
  scripts and automations. Lambdas MUST stay short (one decision or one calculation) and MUST
  NOT duplicate logic that exists elsewhere in the configuration.
- Every script or automation that implements a requirement MUST carry a comment naming the
  requirement id(s) it implements (for example `# FR-004`).
- Every decision rule MUST be covered by at least one manual on-device validation scenario in
  the feature's `quickstart.md`. Host-side unit tests are not required.

Rationale: logic expressed declaratively and labelled with its requirement can be checked by
reading; on-device scenarios then prove the behavior on the real hardware.

### V. Explicit Configuration & Simplicity

- All pin assignments, thresholds, timeouts, and other tunables MUST be named entries in one
  `substitutions:` block at the top of the device YAML; magic numbers in automations, scripts
  and lambdas are forbidden.
- Secrets (WiFi credentials, API encryption key, OTA password) MUST live only in `secrets.yaml`,
  which is git-ignored; a committed `secrets.example.yaml` documents the required keys.
- Every device configuration MUST be accompanied by a pin map (pin → component → direction)
  that matches the YAML.
- The ESPHome version MUST be pinned exactly and recorded in the plan. External components MUST
  be justified in the plan and pinned to an exact version or commit.
- The configuration MUST implement only what the current spec requires (YAGNI). Optional
  ESPHome features (for example `web_server` or `captive_portal`) are added only when the spec
  needs them; unused components MUST be removed before delivery.

Rationale: the configuration is read and adapted by people wiring real hardware; one place to
look for every tunable makes it safe to change.

## Embedded Platform Constraints

- **Firmware**: an ESPHome YAML configuration plus C++ lambdas, as supported by the pinned
  ESPHome version. Lambdas use no exceptions and no RTTI.
- **Target board**: each feature plan MUST name the target board and the ESPHome framework type
  (`arduino` or `esp-idf`). This project's board is the ESP32-C3.
- **Build**: firmware is built and flashed with the ESPHome CLI installed on the development PC.
  `esphome config` MUST validate without errors and `esphome compile` MUST succeed with zero
  compiler warnings originating from project lambdas. The first flash goes over USB; later
  updates may go over the air.
- **Project layout**: one device YAML per device, `secrets.yaml` (git-ignored) with a committed
  `secrets.example.yaml`, and an optional `packages/` folder. ESPHome build output (`.esphome/`)
  is git-ignored. There is no host-side test folder.
- **Home Assistant**: integration uses ESPHome's native API with encryption enabled. All
  communication stays inside the home network; there is no cloud service.
- **Outdoor operation**: the configuration MUST tolerate noisy or briefly disconnected sensors
  (out-of-range readings MUST be treated as invalid, not acted upon) and MUST keep the lamp
  working without WiFi, network, Home Assistant, or a serial monitor. ESPHome's automatic
  reboot timeouts (`wifi: reboot_timeout`, `api: reboot_timeout`) MUST be disabled unless the
  plan justifies otherwise, so losing the network never resets the lamp.
- **Logging**: log verbosity MUST be set by one `logger` level setting. Delivered firmware runs
  at `INFO` or quieter; `DEBUG` is for validation only.

## Development Workflow & Quality Gates

Every delivered change MUST pass these gates in order:

1. **Compile gate**: `esphome config` reports no errors, and `esphome compile` succeeds for the
   named board with zero errors and zero warnings originating from project lambdas.
2. **Resource gate**: the build's memory report is within the limits of Principle III and is
   recorded in the feature's documentation.
3. **Traceability gate**: every functional requirement maps to a named script, automation or
   entity in the YAML and to at least one scenario in the feature's `quickstart.md`; the
   mapping is recorded in the feature's documentation.
4. **Hardware gate**: the feature's `quickstart.md` contains a manual on-device test procedure
   (wiring steps, expected lamp behavior per scenario, including power-cycle recovery and loss
   of network or Home Assistant), every scenario passes, and the pin map matches the YAML.
5. **Review gate**: the configuration is checked against every principle above; any deviation
   is recorded in the plan's Complexity Tracking table with a justification.

The configuration MUST be readable by someone who did not write it: hardware-specific settings
(chipset, timing values, electrical modes) and every non-obvious automation MUST carry a short
comment explaining why.

## Governance

- This constitution supersedes all other practices in this repository. Where a spec, plan,
  task, or device configuration conflicts with it, the constitution wins until it is amended.
- **Amendments** MUST be made through `/speckit-constitution`, MUST state the reason for the
  change, and MUST include a Sync Impact Report listing affected principles and sections.
- **Versioning** follows semantic versioning:
  - MAJOR: a principle or gate is removed or redefined in a backward-incompatible way.
  - MINOR: a principle or section is added or its guidance is materially expanded.
  - PATCH: clarifications, wording, or typo fixes with no change in meaning.
- **Compliance review**: every `/speckit-plan` MUST complete the Constitution Check before
  design and again after it; `/speckit-analyze` MUST flag violations as CRITICAL; deviations
  are allowed only when justified in the plan's Complexity Tracking table.
- Runtime development guidance for agents lives in `CLAUDE.md` once it exists; it MUST NOT
  contradict this constitution.
